# BLE_PACKET_SPEC.md

## Overview

This document defines the BLE discovery payload used by student devices during an active BLE attendance session.

The packet is designed for:

- anonymous device identification
- rolling token validation
- replay resistance in the backend observation workflow
- backend observation metadata handling

## Advertisement UUID

Use a dedicated 128-bit BLE Attendance UUID for the attendance profile. The UUID must be reserved for this module and must not be reused for Wi-Fi attendance logic.

Implementation rule:

- the UUID identifies the BLE attendance service/profile
- the manufacturer data carries the packet payload
- the same UUID is used by the student advertiser and teacher scanner to identify valid attendance traffic

## Manufacturer Data

The manufacturer-specific data field contains only the compact discovery payload.

- Transport encoding: binary
- Byte order: big-endian for multi-byte integer fields
- Total discovery payload size: 24 bytes

## Advertisement Interval

Default active-session advertisement interval:

- nominal: 1000 ms
- acceptable operating range: 750 ms to 2000 ms, subject to platform constraints

The advertisement interval must be stable enough for continuous teacher scanning and should remain active only while the BLE session is open.

## Advertisement Payload

The advertisement payload is the binary manufacturer data published by the student device during a BLE attendance session.

- It carries identity and freshness data needed for teacher-device discovery.
- It must be deterministic so the teacher scanner can decode it without ambiguity.
- It must not contain Wi-Fi fingerprinting data or any shared confidence score.

## Advertisement Size

The fixed payload size is 24 bytes.

- This size is chosen to fit a legacy BLE advertisement with manufacturer-data overhead.
- The payload carries the anonymous identifier and rolling token only.

## Encoding

- Byte order for multi-byte values: big-endian.
- Anonymous Device ID: binary opaque value.
- Rolling Token: binary time-window value or unsigned integer encoded as 8 bytes.
- Timestamp and HMAC are not broadcast over BLE; they are added in the teacher-device observation upload workflow.

## Complete Packet Example

Example packet layout shown as hexadecimal values:

```text
Anonymous Device ID (16 bytes)
12 34 56 78 9A BC DE F0 11 22 33 44 55 66 77 88

Rolling Token (8 bytes)
00 00 00 00 00 1A 2B 3C
```

The teacher scanner reads the packet as a single 24-byte manufacturer-data buffer and slices it by offset:

- bytes `0-15` for Anonymous Device ID
- bytes `16-23` for Rolling Token

## Payload Layout

### Byte Map

| Bytes | Field | Size | Description |
| --- | --- | ---: | --- |
| 0-15 | Anonymous Device ID | 16 bytes | Opaque device identifier for the registered student device. |
| 16-23 | Rolling Token | 8 bytes | Time-window token used to validate freshness and prevent replay. |

## Field Definitions

### Anonymous Device ID

- Size: 16 bytes
- Purpose: uniquely identifies a registered student device without revealing the real hardware identifier
- Encoding: binary opaque value
- Validation: must match a registered device record on the backend

### Rolling Token

- Size: 8 bytes
- Purpose: binds the packet to a short-lived session time window
- Encoding: unsigned integer or fixed binary token, using the same time-window algorithm on client and server
- Validation: must be current for the active BLE scan window and must not be reused outside the valid interval

### Observation Upload Metadata

Timestamp and HMAC are not part of the on-air discovery payload.

- The teacher scanner assigns the observation timestamp when the packet is received.
- The teacher scanner attaches backend-upload metadata before sending the observation batch.
- The backend validates those upload fields as part of the observation workflow.

## Encoding Rules

- All multi-byte numeric values use big-endian encoding.
- The packet is treated as binary data, not as a text string.
- The BLE advertisement layer must preserve byte order exactly as generated by the student device.
- The teacher scanner must forward the raw payload or a lossless decoded representation to the backend.

## Replay Protection

Replay protection uses three checks together:

1. The rolling token must match the active time window.
2. The timestamp must be fresh relative to the current session window.
3. The backend must reject duplicate `(anonymous_device_id, rolling_token, timestamp)` combinations within the same validity window.

If a packet is captured and rebroadcast later, at least one of these checks will fail.

## Teacher Scanner Extraction

- The teacher scanner extracts the payload in three steps.

1. Match the advertisement UUID against the BLE attendance UUID.
2. Read the manufacturer data as a 24-byte binary buffer.
3. Slice the buffer by the fixed offsets defined in the payload layout.

The scanner should preserve the raw bytes or a lossless binary representation so backend upload metadata can be derived consistently.

## Backend Validation

The backend validates the payload in the same fixed order every time.

1. Confirm the session is an active BLE session.
2. Resolve the Anonymous Device ID against `ble_registered_devices`.
3. Validate the Rolling Token against the current time window.
4. Validate the scanner-provided timestamp against the allowed clock skew.
5. Validate the scanner-provided upload digest or HMAC metadata.
6. Reject duplicates and replayed payloads before writing observations.

## Packet Validation Flow

1. Teacher device scans the advertisement.
2. Teacher filters the packet by the BLE Attendance UUID.
3. Teacher uploads the raw observation payload.
4. Backend resolves the anonymous device ID to a registered student.
5. Backend validates the rolling token and observation metadata.
6. Backend records the observation and updates attendance generation state.

## Notes

- The packet layout is fixed-width so validation is deterministic and cheap.
- The design intentionally keeps the packet independent from Wi-Fi fingerprinting.
- Any future protocol revision should preserve the separation between identity, freshness, and authenticity fields.
