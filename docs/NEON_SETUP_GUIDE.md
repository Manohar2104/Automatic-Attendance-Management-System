# Neon Setup Guide (PostGIS + Phase 2)

This guide explains how to prepare a Neon PostgreSQL database for Phase 2 of Smart Attendance Registry, including enabling PostGIS and preparing migration execution.

IMPORTANT: Do NOT store Neon credentials in source control. Use CI secrets or environment variables to provide `DATABASE_URL` and `DIRECT_URL`.

## Key environment variables

- `DATABASE_URL` — Neon pooler URL (use for application runtime connections)
- `DIRECT_URL` — Neon direct/admin URL (use only for administrative operations such as creating extensions)

## Steps

1. Verify Neon connectivity (pooler):

```bash
export DATABASE_URL="<neon_pooler_url>"
psql "$DATABASE_URL" -c 'SELECT 1;'
```

2. Check whether PostGIS is enabled:

```bash
psql "$DATABASE_URL" -c "SELECT extname FROM pg_extension WHERE extname = 'postgis';"
```

3. Enable PostGIS if missing (use DIRECT_URL):

On Neon, extension creation may require the direct/admin connection. Use DIRECT_URL stored as a secret.

```bash
export DIRECT_URL="<neon_direct_url>"
psql "$DIRECT_URL" -c "CREATE EXTENSION IF NOT EXISTS postgis;"
psql "$DIRECT_URL" -c "CREATE EXTENSION IF NOT EXISTS postgis_topology;"
```

4. Verify PostGIS:

```bash
psql "$DATABASE_URL" -c "SELECT PostGIS_Full_Version();"
```

5. Run Phase 2 migrations in staging first (do NOT run in production without backup):

```bash
# In the project root — this migration runner reads files in migrations/
export DATABASE_URL="<neon_pooler_url>"
node backend/dist/src/scripts/migrate.js
```

Notes and cautions:
- Use `DIRECT_URL` for extension creation; the pooler URL may not have the permission to create extensions.
- Always snapshot Neon before running destructive migrations or rollbacks.
- Migration scripts generated by this project are idempotent and include `IF NOT EXISTS` guards.
